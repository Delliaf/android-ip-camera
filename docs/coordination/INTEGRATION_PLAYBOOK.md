# Интегратор: как объединять результаты независимых чатов

**Важное различие:** обычный исполнитель пишет свою ветку/PR/session. **Интегратор** отвечает за конфликты, целостный тестовый APK, обновление общих справочников, порядок merge. Не становиться интегратором самовольно.

## До интеграции

1. Через live GitHub API найти все открытые PR, base/head SHA, файлы, связи, tests, последний коммит.
2. По `main/docs/sessions/**` и `main/docs/workstreams/**` прочитать записи каждого исполнителя, включая причины, ограничения и скопление задач.
3. Построить DAG зависимостей. Снимок по 2026-11-20: `main → PR1`; отдельно PR2 от PR1 и ветка `PR1 → PR3 → PR4 → PR5`. PR2 не является частью PR3–PR5 автоматически.
4. У каждого участника запросить только **отсутствующие** проверки/контекст, которые GitHub не содержит. Не повторять известные требования.
5. Не "усреднять" версии файлов: сравнить diff/методы/Kotlin package/API/Gradle/dependencies, конфликты между Camera2, SurfaceTexture, StreamingService, ONVIF, HTML и пользователями сервиса.

## Merge и release-кандидат

- **Безопасная политика:** пока экспериментальные PR помечены draft или H872 не проверен, мержить в `main` только с явным одобрением пользователя.
- При объединении создать **собственную integration branch**, не перезаписывать ветки исполнителей.
- Вносить изменения в порядке зависимостей; общие Kotlin-файлы править семантически, а не механическим копированием старой версии.
- С каждым изменением обновить тесты, выполнить CI по точному SHA, проверить arm64 APK, разрешить конфликты между ONVIF, CameraX/Direct, benchmark, root-metrics.
- Требования качества: пользователю важнее высокая реальная детализация, чем цифра "4K" в интерфейсе; hardware readback и тесты по кадрам обязательны.
- После аппаратного теста H872 создать отчёт `docs/sessions/YYYY-MM-DD/integration-<id>.md` в main с final SHA, artifact, проверенной firmware/Android, фактическими кадрами/FPS/thermal и известными ограничениями (без публикации приватных данных).
- Обновить **только интегратором** `BRANCHES_AND_PRS.md`, `START_HERE.md`, справочники доменов и при необходимости ADR, чтобы будущие чаты начинали с актуальной картины.

## Чего НЕ делать

- Не мерджить автоматически green CI/draft PR, не объявлять тест на железе из JVM-прогона.
- Не запускать несколько агентов на одном branch/общем history файле.
- Не удалять старые journal записи: историю ошибок, отказов и гипотез сохранять.
- Не переносить root/проприетарные HAL-библиотеки в публичный репозиторий без отдельного безопасного разрешения.
- Не верить только статическому списку PR: всегда сверять GitHub API.

## Результат интегратора

Один интеграционный PR (или несколько зависимых), валидная цепочка merge, матрица тестов, сборка на конкретном SHA, технический отчёт и обновлённые общие указатели. Тогда новые чаты могут безопасно начинать следующую задачу независимо друг от друга.
