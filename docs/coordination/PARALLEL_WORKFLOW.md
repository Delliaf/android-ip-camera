# Протокол независимых параллельных чатов

## Принцип

Новый чат может ничего не знать о других чатах. **Всё необходимое для продолжения хранится в GitHub**, не только в диалоге: код в ветке/PR, выводы и ограничения в main/docs. Каждый исполнитель самостоятельно читает актуальную историю и добавляет свою.

## 1. Перед работой (read first)

- Читай `main/AGENTS.md`, `main/docs/coordination/START_HERE.md`, эту инструкцию.
- Живым GitHub API получи список веток, открытых PR, `base/head`, SHA, последние CI и изменённые файлы PR.
- Подбери **верную основу**, особенно если нужные функции ещё не объединены с `main`. Пример: задача по телеметрии зависит от `fix/lg-g6-metrics-visible`; задача по CameraX может зависеть от `feature/manual-camera-4k-stream`. Не переписывай более новую реализацию по старому файлу.
- Ознакомься с доменной документацией и недавно изменёнными `docs/sessions/` (GitHub tree/search, а не только индекс).

## 2. Правила владения

- **Один чат — одна рабочая ветка и собственный draft PR**. Имя `feat/<slug>-<unique>` или `fix/<slug>-<unique>`; не переиспользуй ветку другого чата.
- Не пушь в чужую ветку и не редактируй его файл сессии. Если задача пересекается, сохрани зависимость/блокер в своём файле и предложи PR поверх нужной базы.
- **Стабильный `main` остаётся без незавершённого экспериментального кода**. Прямые записи в `main` разрешены **только** для независимых, неисполняемых текстовых файлов истории внутри `docs/sessions/` и `docs/workstreams/<domain>/<task-id>.md` (а также отдельного ADR по новой теме); существующие общие файлы менять по согласованию интеграции.
- Не редактируй одновременно `main/AGENTS.md`, `START_HERE.md`, `BRANCHES_AND_PRS.md`, общий `DEVELOPMENT_HISTORY.txt` или шаблоны. Их обслуживает интегратор после просмотра связанных PR.
- **Уникальный путь журнала**: `docs/sessions/YYYY-MM-DD/<topic>-<chat-unique-id>.md`. Создай новый файл; при продолжении того же чата редактируй **только свой** файл по актуальному content SHA. При конкурирующем изменении сначала fetch + merge, без force-push.
- Для больших функций веди **подробный файл** `docs/workstreams/<domain>/<feature-unique-id>.md`: ключевые требования, архитектура, изменения по файлам и функциям, API/команды, edge cases, журналы тестов и результаты. В `docs/sessions` — хронология, ссылки и handoff.
- Каждая запись содержит ссылки на PR/ветку/точный SHA/Actions (не только номера), статус `planned/working/blocked/CI-passed/device-verified/done`, что подтверждено и что нет.

## 3. Пример рабочего цикла

1. Просмотр реального HEAD/PR, чтение документов и проектирование.
2. Создание собственного `docs/sessions/...` в `main` **до первого коммита кода**: задача, выбранная base, план, соседние PR.
3. Создание своей ветки от правильной base. Пишешь код, тесты, маленькие коммиты, обновляешь свой журнал. Для глубоких исследовательских задач создаёшь доменный файл.
4. Публикуешь **draft PR в ту ветку, от которой ответвился**. В PR отмечаешь dependencies, тесты, совместимость, ограничения и ссылку на свой журнал в `main`.
5. Смотришь точный SHA CI; не утверждаешь успешный APK по старому запуску. Сохраняешь результат / проблему и следующий шаг.
6. После результатов телефона дополняешь оригинальную запись (не удаляя прежние выводы); если код менялся, повторно запускаешь CI.
7. Не мержишь чужие ветки или draft PR самовольно. Для интеграции передавай владельцу/интегратору список PR в нужном порядке.

## 4. Типичные конфликты и их профилактика

- **Два чата трогают один Kotlin-файл:** разные feature-ветки, каждый PR указывает изменённые функции, один интегратор переносит изменения после сверки. Никаких blind cherry-pick/force-push.
- **Два чата пишут историю:** отдельные session/workstream-файлы в `main`. Не добавлять оба текста в общий гигантский `DEVELOPMENT_HISTORY.txt`.
- **Feature ещё не в main:** базироваться на актуальной зависимой ветке или явно документировать, как перенести изменение после merge.
- **Документ противоречит коду:** приоритет у проверенного исходника + живого CI/лога для соответствующего SHA; **исправить документ** и отметить, где ошибка, а не скрывать расхождение.
- **Нет write-права в main:** не лгать, что журнал общий; создать запись в своей PR-ветке, затем открыть отдельный documentation PR в `main` и сообщить пользователю, что данные ещё не общедоступны в main.
- **Неактуальные заметки:** не использовать статус "working" как доказательство текущей работы чужого чата; проверять время последнего коммита и фактический GitHub PR/Checks.

## 5. Выходной контракт для нового чата

Перед завершением должны существовать: ссылка на изменённую ветку/PR, **обновлённая запись в GitHub main** либо явный блокер доступа, список проверок с точными SHA, результат/ошибки, что делать дальше. Никогда не обещать фоновые действия без настроенной автоматизации.
