# ADR-0001 — Параллельные независимые чаты, GitHub как источник контекста

**Статус:** accepted · **Дата:** 2026-11-20

## Контекст

Пользователь ведёт несколько разработок форка Android IP Camera в разных чатах. Память чатов может быть недоступна другой модели. Ранее один большой `DEVELOPMENT_HISTORY.txt` (десятки тысяч символов) дописывался в экспериментальной ветке; одновременное редактирование одной и той же ветки и файла создаёт гонки, конфликт SHA и потерю информации. `main` не содержит экспериментальные кодовые функции, а ветки имеют stacked PR.

## Решение

- Каноническая постоянная точка входа `main/AGENTS.md` и `main/docs/coordination/START_HERE.md`.
- Для каждого независимого чата **уникальный** файл сессии `main/docs/sessions/YYYY-MM-DD/<slug-id>.md`. Это всегда общая история, видимая другим чатам, без необходимости merge experimental PR.
- Для детальной задачи отдельный подробный `main/docs/workstreams/<domain>/<slug-id>.md`. Доменные справочники и индексы — редактирует интегратор, а независимые чаты читают.
- Код только на своей feature/fix branch, правильный base, открытый draft PR с зависимостями. `main` остаётся без незавершённого экспериментального кода.
- Исторический большой журнал архивируется и больше не является общим конкурентно редактируемым местом.
- Код, реальная CI и логи с точным SHA имеют приоритет перед текстовым утверждением «работает». Непроверенные аппаратные гипотезы помечаются явно.

## Альтернативы

- «Каждый чат помнит всё сам» — невозможно гарантировать доступ и полноту контекста.
- «Каждый чат пишет один общий HISTORY.txt» — высокая вероятность перезаписи и конфликтов при параллельном GitHub API.
- «Все коммитят одну feature branch» — нельзя различить авторство, конфликты, тестируемые SHA и откат.
- «Всю историю хранить только в PR» — PR может закрыться или остаться в чужой независимой ветке; новый чат должен иметь стабильную точку входа.

## Последствия

Нужно создавать и обновлять записи в GitHub **во время** разработки (не обещать сделать после сессии). Если нет прав записи в main, агент должен зафиксировать проблему, оставить файл в отдельном docs PR и явно признать, что канал общей памяти не завершён.
